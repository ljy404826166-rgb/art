# 微信小程序画家头像图片补全实施计划

**文档状态：** 已修订，待逐项执行  
**制定日期：** 2026-07-26  
**修订日期：** 2026-07-26  
**实施范围：** `miniapp/` 画家列表、画家详情、关注画家页，以及生产 `artists` 集合  
**核心目标：** 以现有画家信息体系为唯一主数据源，完成全部生产可见画家记录的头像候选搜索、代表关联审核、版权审核、人工筛选、图片处理、受控上传、原记录回写和最终验收

## 1. 目标与完成定义

本项目不以“强行让每条记录都有一张图片”为完成标准，而以“每条生产画家记录都得到准确、可解释、可追溯的处理结论”为完成标准。

头像优化不是一套独立于画家数据的平行系统。现有生产 `artists` 集合负责定义“处理谁、是谁、与哪些作品关联”，头像审核流水线只补充图片证据和审核过程，最终展示字段仍回写同一个画家记录。

全部生产可见记录必须进入以下一种最终状态：

| 最终状态 | 含义 | 前台表现 |
|---|---|---|
| `approved` | 已找到与画家关联明确、授权可用、质量合格的代表性头像 | 显示头像图片 |
| `no_eligible_asset` | 已完成检索，但没有找到授权与质量均合格的图片 | 保留文字头像 |
| `non_person_entity` | 机构、工作室、画派归属、匿名等非自然人实体 | 使用明确的非人物回退样式 |
| `identity_unresolved` | 当前身份不足以可靠匹配人物图片 | 保留文字头像，不猜测 |
| `rights_blocked` | 找到图片，但授权不明或不满足项目使用条件 | 不上线图片 |

项目完成时必须达到：

- 生产画家清单处理覆盖率为 100%。
- 所有上线头像与目标画家的代表关联率为 100%，不允许与画家无关的“相似人物”或同名误配。
- 所有上线肖像均保存来源页、作者或创作者、许可证和审核记录。
- 所有上线图片均托管在项目自己的受控存储，不依赖外站热链。
- 所有页面在图片缺失、加载失败或离线时仍显示原有文字头像。
- 生产数据库写入具备备份、试运行、幂等、校验与回滚能力。

## 2. 当前基线

### 2.1 前端现状

- 画家列表页通过 `item.avatarText` 渲染文字头像。
- 画家详情页通过 `artist.avatarText` 渲染文字头像。
- 关注画家页也保存并渲染 `avatarText`。
- `miniapp/services/artists.js` 的云查询字段投影和标准化结果尚未读取肖像 URL。
- 图片失败后的文字回退逻辑尚未抽成可复用组件。

### 2.2 数据现状

- 规范化画家 Schema 已预留：
  - `portrait_url`
  - `portrait_source`
  - `portrait_license`
- 现有 Schema 还包含可直接提高搜索和审核效率的字段：
  - `_id`
  - `name_zh`、`name_en`、`aliases`
  - `birth_year`、`death_year`、`lifespan_text`
  - `entity_type`、`identity_status`
  - `authority_ids`
  - `sources`
  - `representative_artwork_ids`
  - `review_status`
- 现有 `avatar_text` 继续作为永久回退字段，不删除。
- 当前最新本地生产迁移产物包含约 117 条画家记录；任务 1 必须重新从生产云数据库导出，以实际生产可见清单为唯一范围基线。
- 既有画家治理审计中存在自然人、机构、工作室、归属描述、匿名和未解析实体，不能对所有记录套用人物肖像搜索。
- 作品记录已经通过稳定 `primary_artist_id` / `artist_ids` 与画家关联，可用于优先发现项目现有自画像、画家肖像和相关作品。
- 项目已使用腾讯 COS 托管作品图片，可复用现有上传、重试、校验和回滚思路，为画家肖像建立独立前缀。

### 2.3 当前页面覆盖范围

本次必须同步覆盖：

1. `pages/artists` 画家列表。
2. `pages/artist-detail` 画家详情。
3. `pages/followed-artists` 关注画家。
4. `services/local-library.js` 中关注画家的本地快照与旧数据兼容。
5. 后续如果画家分享卡片使用头像，再统一复用相同字段。

### 2.4 与现有画家信息体系的结合方式

采用“一个画家主记录、一个过程审核清单、一个图片存储层”的结构：

```text
生产 artists 集合
├─ 身份：_id、姓名、别名、生卒年、实体类型
├─ 权威依据：authority_ids、sources、identity_status
├─ 作品关系：representative_artwork_ids、artworks.artist_ids
└─ 最终头像：portrait_url、source、license、status
          │
          ├─ 头像审核清单
          │  ├─ 候选、身份与版权证据
          │  ├─ 采用/拒绝决定
          │  └─ 处理、上传与审核记录
          │
          └─ 腾讯 COS
             └─ 版本化头像文件
```

字段与效率关系：

| 现有画家字段 | 头像流程用途 |
|---|---|
| `_id` | 队列主键、COS 对象路径、数据库回写和幂等键 |
| `name_zh` / `name_en` / `aliases` | 自动生成多语言检索词 |
| 生卒年、国家和地区 | 排除同名人物和年代错误 |
| `entity_type` | 自动区分自然人与非人物实体 |
| `identity_status` | 阻止未解析身份进入自动人物匹配 |
| `authority_ids.wikidata` | 精确获取 Wikidata `P18` 和 Commons 候选 |
| `sources` | 优先访问已确认的博物馆、档案馆和权威页面 |
| `representative_artwork_ids` | 优先检查项目内已有自画像或可靠人物肖像 |
| `review_status` | 自动限定生产可见处理范围 |
| `primary_artist_id` / `artist_ids` | 稳定连接现有作品，避免依赖姓名文本匹配 |

集成边界：

- 不新建另一套包含姓名、简介、流派和作品的“头像画家库”。
- 审核清单通过 `artist_id` 引用现有画家，不复制并长期维护整份画家资料。
- 图片二进制文件不写入数据库，只在画家记录中保存受控 URL。
- 简介、流派或作品信息更新后，头像关系仍通过稳定 `_id` 保持有效。
- 搜索时可以使用流派和作品作辅助上下文，但不能仅凭风格相似判断人物身份。

## 3. 已确认的实施原则

### 3.1 代表关联明确优先

- 先核对画家稳定 ID、英文名、生卒年和 Wikidata QID，再搜索图片。
- 同名、姓名变体、父子同名、工作室归属等情况必须单独核验。
- 画家身份未解析时不使用搜索结果中的“相似人物”，但可以使用与其稳定作品关系或权威资料明确关联的代表性视觉资源。
- 图片不要求一定是经严格认证的画家本人照片；可以是本人照片、自画像、历史肖像、传统归属肖像、代表作局部或艺术化头像。
- 来源页、馆藏页、稳定作品关系或其他可靠资料必须能够说明该图片为何代表当前画家；仅在文章中出现或被搜索引擎关联不构成证据。
- 对身份存疑的历史肖像必须在审核清单中如实标注，不得在产品元数据中宣称为已认证的本人照片。

### 3.2 图片类型优先级

在代表关联与版权均合格的前提下，按以下顺序筛选：

1. 可核验的本人照片。
2. 有明确作者和人物说明的历史肖像。
3. 画家的自画像。
4. 有可靠馆藏或档案说明的素描、版画、雕塑或半身像。
5. 被权威资料或长期通行用法明确关联到画家的传统肖像。
6. 具有稳定作品关系和鲜明辨识度的代表作局部或开放授权艺术头像。
7. 无合格资源时保留文字头像。

不采用：

- 与画家没有可解释关联、仅凭风格相似生成或挑选的“艺术头像”。
- 现代作者重新绘制但没有开放许可的插画。
- Pinterest、普通博客、社交媒体、搜索结果缩略图。
- 带明显水印、严重失真、过度修复或错误着色的图片。
- 只适用于新闻报道或合理使用、但不允许独立复用的图片。

### 3.3 来源优先级

1. Wikimedia Commons 的单个文件说明页。
2. 博物馆、美术馆、国家图书馆、档案馆的开放获取资源。
3. Wikidata `P18` 指向的 Commons 文件，用作候选发现入口。
4. 其他明确提供公共领域或开放许可证说明的机构资源。
5. 普通网页和图片搜索只用于发现线索，不直接作为下载与授权依据。

### 3.4 许可证准入规则

优先接受：

- Public Domain / Public Domain Mark。
- CC0。
- CC BY，并完整保留署名与许可证链接。

条件接受：

- CC BY-SA。只有在裁切、压缩和分发方式能够满足署名、改动说明及相同方式共享要求时才能通过。
- 机构自有 Open Access 许可。必须逐条确认允许公开展示、裁切和重新托管。

直接拒绝：

- 授权不明。
- All Rights Reserved。
- 仅限合理使用。
- 仅限非商业使用但项目未来用途无法保证为非商业。
- 禁止演绎且头像需要裁切处理。
- 仅允许在原站嵌入或禁止重新托管。

Wikimedia Commons 明确说明每个文件可能具有不同署名和许可证要求，且不建议直接热链；因此必须逐文件核验，而不能把“来自 Commons”直接视为审核通过。

## 4. 数据模型与审核清单

### 4.1 生产 `artists` 字段

保留现有字段并补充以下最小展示字段：

```js
{
  portrait_url: "https://受控域名/artist-portraits/artist-id/v1/portrait-512.webp",
  portrait_source: "https://commons.wikimedia.org/wiki/File:...",
  portrait_license: "Public Domain",
  portrait_credit: "Creator / Institution",
  portrait_kind: "photograph",
  portrait_artwork_id: "",
  portrait_status: "approved",
  portrait_updated_at: "2026-07-26T00:00:00.000Z",
  avatar_text: "莫"
}
```

约束：

- 只有 `portrait_status = approved` 时，生产记录才允许写入 `portrait_url`。
- `avatar_text` 永远保留，作为图片失败和特殊实体的回退。
- `portrait_source` 必须指向文件说明页或机构对象页，不指向搜索结果页。
- 如果头像来自项目现有作品，必须写入 `portrait_artwork_id`；否则保持为空。
- `portrait_artwork_id` 必须指向真实存在且与该画家稳定关联的作品，不得只凭标题文本推断。
- 不把临时本地路径、第三方缩略图地址或待审核图片写入生产记录。

### 4.2 完整审核清单

完整证据保存在独立 JSONL/CSV 清单中，不把所有治理字段塞入前端查询：

| 字段 | 说明 |
|---|---|
| `artist_id` | 项目稳定画家 ID |
| `name_zh` / `name_en` | 审核时使用的姓名 |
| `entity_type` / `identity_status` | 实体边界 |
| `authority_ids.wikidata` | Wikidata QID |
| `candidate_origin` | 项目现有作品、Wikidata、Commons、机构资源或人工发现 |
| `portrait_artwork_id` | 候选来自现有作品时的稳定作品 ID |
| `candidate_rank` | 同一画家的候选排序 |
| `portrait_kind` | 照片、历史肖像、自画像、传统归属肖像、代表作或艺术头像等 |
| `file_page_url` | 文件说明页 |
| `original_file_url` | 原始文件下载地址 |
| `creator` | 摄影师或作品作者 |
| `institution` | 馆藏或提供机构 |
| `license` / `license_url` | 标准化许可证及链接 |
| `credit_line` | 可直接用于产品展示的署名 |
| `representation_evidence` | 证明图片与画家存在明确代表关联的依据 |
| `identity_evidence` | 如图片声称表现画家本人，记录其身份确定程度；不作为所有头像的强制门槛 |
| `rights_status` | 通过、条件通过、拒绝 |
| `quality_status` | 分辨率、清晰度和裁切适用性 |
| `review_decision` | 选用、备选、拒绝 |
| `review_notes` | 决策说明 |
| `reviewed_by` / `reviewed_at` | 审核责任记录 |
| `source_sha256` | 下载原文件哈希 |
| `processed_sha256` | 处理后文件哈希 |
| `crop` | 裁切坐标或策略 |
| `modifications` | 裁切、缩放、格式转换说明 |

## 5. 图片规格与存储规范

### 5.1 处理规格

- 原始文件先保存到本次运行产物目录，记录 URL、尺寸、MIME 和 SHA-256。
- 不使用生成式扩图、换脸、美化、补画或自动着色。
- 只允许方向纠正、方形裁切、缩放、轻度锐化和格式转换。
- 人脸、头肩或其他核心代表元素位于圆形安全区内，不能切掉关键识别特征。
- 处理输出：
  - 512 × 512 WebP，作为统一展示资源。
  - 建议单张不超过 120 KB。
  - 移除 EXIF、GPS 和无关元数据。
- 若 WebP 真机兼容验证失败，则输出 512 × 512 JPEG 作为统一格式。

### 5.2 COS 路径

采用版本化、不可变对象键：

```text
artist-portraits/{artist_id}/v1/portrait-512.webp
```

规则：

- 头像变更使用 `v2`、`v3`，不覆盖旧版本。
- 数据库验证成功后再解除旧版本引用。
- 设置正确的 `Content-Type` 和长期缓存头。
- COS 地址必须使用小程序现有已备案/已配置的受控域名。
- 图片上传成功并通过 HTTP、尺寸、MIME 与哈希校验后，才能更新数据库。

## 任务 1：冻结生产范围与建立处理台账

**目标：** 得到本次必须处理的唯一画家清单和可恢复基线。  
**依赖：** 无。  
**状态：** 已完成。

实施内容：

2. 同步导出与这些画家关联的作品关系和头像候选所需字段：
   - `primary_artist_id`
   - `artist_ids`
   - 作品标题与受控题材标签
   - 原始来源与版权字段
   - 已有图片 URL
3. 保存只读生产备份，记录环境 ID、导出时间和记录总数。
4. 对比本地最新迁移产物，报告新增、缺失、重复和字段差异。
5. 为每条记录补齐或确认：
   - 稳定画家 ID。
   - 中英文名。
   - 生卒年。
   - 实体类型。
   - 身份状态。
   - Wikidata QID 或未解析原因。
6. 使用稳定画家—作品关系识别项目内部可能存在的：
   - 自画像。
   - 由他人创作且明确表现该画家的肖像。
   - 可作为候选但仍需版权和身份审核的作品。
7. 生成头像处理总台账、现有作品候选清单和批次优先级。

建议产物：

```text
outputs/artist-portraits/{run-id}/
├─ production-backup.jsonl
├─ scope.json
├─ artist-portrait-queue.csv
├─ existing-artwork-candidates.jsonl
└─ baseline-report.json
```

验收标准：

- 生产记录总数明确。
- 每条记录恰好出现一次。
- 自然人与非人物实体已分开。
- 身份未解析项不会进入自动肖像匹配。
- 画家—作品候选全部通过稳定 ID 关联，不使用姓名模糊匹配作为最终关系。
- 台账中的姓名、简介、流派和作品等上下文均来自现有画家信息体系。
- 生产备份可被现有管理脚本重新导入。

回滚边界：

- 本任务只读，不修改数据库。

## 任务 2：扩展数据模型并建立共享肖像组件

**目标：** 在没有任何新图片的情况下，先让前端支持“图片优先、文字回退”。  
**依赖：** 任务 1。  
**状态：** 已完成。

实施内容：

1. 更新画家 Schema 和数据治理文档。
2. 在 `CLOUD_ARTIST_LIST_FIELDS` 中读取肖像展示字段。
3. 在 `normalizeCloudArtist` 和本地数据标准化中输出：
   - `portraitUrl`
   - `portraitSource`
   - `portraitLicense`
   - `portraitCredit`
   - `portraitKind`
   - `portraitArtworkId`
   - `portraitStatus`
4. 新建可复用的 `artist-portrait` 组件：
   - `portraitUrl` 存在且已批准时显示 `<image mode="aspectFill">`。
   - 图片加载失败时自动切换为 `avatarText`。
   - 列表页启用懒加载。
   - 支持列表、详情和关注页三种尺寸。
5. 画家列表、详情和关注画家页统一使用组件。
6. 更新关注画家的本地快照结构，并兼容旧快照中只有 `avatarText` 的情况。
7. 详情页为需要署名的图片提供“肖像来源与授权”展示入口。

验收标准：

- 旧数据库没有任何 `portrait_url` 时，页面视觉和功能无回归。
- 模拟有效图片时，三个页面都显示圆形肖像。
- 模拟 404、超时或空 URL 时立即显示文字回退。
- 已关注的旧画家记录不会因字段升级丢失。
- 图片不改变卡片高度、文本截断和滚动分页行为。

回滚边界：

- 移除新组件调用即可恢复原文字头像。
- 不删除 `avatar_text`。

## 任务 3：建立现有作品优先的候选搜索与元数据采集流水线

**目标：** 先复用现有画家和作品体系，再通过权威外部来源补充候选；自动生成候选，但不自动决定上线图片。  
**依赖：** 任务 1。  
**状态：** 已完成。

建议脚本：

```text
scripts/artist-portraits/
├─ export-portrait-scope.mjs
├─ fetch-portrait-candidates.mjs
├─ build-portrait-review-sheet.mjs
└─ audit-portrait-candidates.mjs
```

实施内容：

1. 从任务 1 的现有作品候选中优先提取自画像和可靠人物肖像。
2. 对每个现有作品候选复用并核验：
   - 画家与作品的稳定 ID 关系。
   - 作品来源页。
   - 原始版权状态。
   - 当前 COS 图片是否适合制作头像。
3. 只有现有作品候选不合格或不存在时，才进入外部搜索。
4. 对具有 Wikidata QID 的自然人读取 `P18` 图片声明。
5. 通过 Commons 文件 API 获取：
   - 文件说明页。
   - 原始下载地址。
   - 作者。
   - 许可证名称和链接。
   - 署名文本。
   - 分辨率和 MIME。
6. 对没有合格 `P18` 图片的画家，使用现有姓名、别名和生卒年自动生成以下人工检索词：
   - `"英文名" portrait`
   - `"英文名" photograph`
   - `"英文名" self portrait`
   - `"英文名" drawing`
   - `"英文名" Wikimedia Commons`
7. 将画家已有 `sources` 中的博物馆、档案馆和权威页面加入定向搜索。
8. 每位自然人最多保留 3 个候选，并记录候选来自“现有作品”还是“外部资源”。
9. 自动拒绝授权不明、尺寸过小、格式异常或人物说明不匹配的候选。
10. 输出候选 JSONL、审核 CSV 和候选联系表。
11. 限速、重试并缓存外部 API 结果，避免重复请求。

验收标准：

- 候选来源可追溯到具体文件说明页。
- 来自现有作品的候选可追溯到 `portrait_artwork_id` 和当前画家 ID。
- API 失败不会产生空白“已通过”记录。
- 同一文件按标准化 URL 或哈希去重。
- 同一画家的现有作品候选与外部候选在一张审核表中统一排序。

## 8. 风险与应对

| 风险 | 应对 |
|---|---|
| 搜索到同名或相似人物 | 使用稳定 ID、生卒年、QID 和文件说明四重核验 |
| 另建头像名单导致画家资料重复和漂移 | 生产 `artists` 作为唯一主数据源，审核清单只保存 `artist_id` 与过程证据 |
| 现有作品标题含“自画像”但作者关系不成立 | 同时核对 `portrait_artwork_id`、`primary_artist_id` / `artist_ids` 和作品来源 |
| 图片来自 Commons 但许可证要求不同 | 逐文件保存许可证，不按站点整体放行 |
| CC BY-SA 裁切后义务不明确 | 默认降级为条件审核，优先寻找 PD/CC0/CC BY 替代 |
| 找不到某位画家肖像 | 记录 `no_eligible_asset`，保留文字头像 |
| 机构或匿名记录没有人物 | 使用 `non_person_entity` 回退，不生成虚假人物 |
| 外站图片地址失效 | 下载后上传受控 COS，不使用热链 |
| 自动裁切切掉头部 | 生成联系表并允许逐图保存裁切坐标 |
| 一次全量写入风险过高 | 先 20 位试点，再按 20 位分批发布 |
| 关注页仍保存旧文字快照 | 增加快照版本和按画家 ID 刷新逻辑 |
| 图片增加首屏流量 | 512 WebP、限体积、列表懒加载、长期缓存 |
| 后续来源页或许可证变化 | 保留审核清单与访问日期，定期执行 URL/元数据审计 |
