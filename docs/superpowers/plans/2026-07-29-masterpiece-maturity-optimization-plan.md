## 1. 计划目的

Masterpiece 已经具备完整的作品浏览、搜索、分类、画家、收藏、历史、账号、成就、客服和法律信息体系。后续工作不再以快速增加功能为主，而是把项目提升到可以持续发布、稳定运营、可靠回滚和量化优化的成熟产品状态。

本计划将审计中发现的问题拆成可独立执行和验收的任务。后续每完成一项任务，都应在本文件中更新：

- 状态；
- 实际修改范围；
- 自动化验证结果；
- 人工或真机验收结果；
- 尚未解决的问题；
- 回滚文件或恢复方式。

## 2. 是否可以解决

可以。当前问题没有显示出需要推翻现有产品或重写全部小程序的情况。

问题主要分为五类：

1. 生产数据版本漂移；
2. 本地与发布门禁失效；
3. 依赖安全和运维工具可靠性不足；
4. 缺少持续集成与产品观测；
5. 可访问性、设计系统和代码结构仍有优化空间。

解决策略是保留现有产品功能与视觉，在此基础上逐层恢复可信门禁，再进行体验和架构治理。

## 4. 最终目标

全部任务完成后，项目应达到以下状态：

1. 仓库、小程序和 Web 只有一套明确的启动说明和受支持入口；
2. 任意受支持工作路径执行构建和测试结果一致；
3. 格式、静态检查、单元测试、E2E、开发者工具冒烟全部通过；
4. 生产分类关系、频道计数和推荐查询处于同一发布版本；
5. 生产审计返回 `ok: true`；
6. 生产依赖不存在未豁免的 critical/high 风险；
7. CloudBase 审计可以重试、续跑并生成可恢复报告；
8. 每次提交和正式发布都有自动化门禁；
9. 推荐、搜索、图片和云端降级具备隐私友好的可观测能力；
10. 主要交互满足语义、命中区和颜色对比度要求；
11. 视觉令牌和共享组件能够防止同类页面再次出现参数漂移；
12. Android 与 iOS 真机完成最终发布回归。

## 5. 执行原则

### 5.1 保护现有修改

当前工作区存在大量尚未提交的既有修改。执行任何任务时必须：

- 不使用 `git reset --hard`；
- 不用签出旧版本覆盖用户修改；
- 不清理与当前任务无关的未跟踪文件；
- 修改前先确认目标文件是否包含未提交内容；
- 每个任务只修改明确列入范围的文件。

### 5.2 数据写入规则

所有生产数据修复必须遵循：

1. 只读审计；
2. 生成确定性修复计划；
3. 保存写入前快照；
4. dry-run；
5. 小批量 pilot；
6. 回读验证；
7. 正式写入；
8. 再次生产审计；
9. 保留 rollback 文件。

### 5.3 发布规则

任何单项测试通过都不能替代完整发布门禁。正式上传前至少需要：

- 本地完整门禁；
- CI 完整门禁；
- 开发者工具预览；
- Android 真机；
- iOS 真机；
- 生产数据只读审计；
- 回滚文件和回滚步骤。

### 5.4 状态定义

| 状态 | 含义 |

| 待执行 | 尚未开始 |
| 执行中 | 正在修改或验证 |

## 7. 任务一：统一项目入口并固化基线

### 7.1 问题

当前存在三种路径差异：

- `D:\art` 是指向 `E:\CodexProjects\art` 的 Junction；
- Web 构建从 `D:\art` 失败，从真实路径执行成功；
- 仓库根目录和 `miniapp` 目录各有一份开发者工具配置，根目录配置没有正确的小程序根路径。

从仓库根目录启动开发者工具时，模拟器出现 `timeout`；从 `miniapp` 目录启动正常。

### 7.2 目标

形成一套明确、可移植、可以被脚本和 CI 复用的项目入口。

### 7.3 最终实施方案

1. 将仓库真实路径作为脚本计算基准，不直接依赖盘符；
2. 仓库根目录是 npm、构建、测试和数据脚本的唯一命令入口；
3. `miniapp/` 是微信开发者工具的唯一工程入口，其配置明确：
   - `miniprogramRoot: "./"`；
   - `cloudfunctionRoot: "cloudfunctions/"`；
   - 固定基础库版本和 AppID；
4. 仓库根目录不再保留第二份 `project.config.json`，入口检查会拒绝重复配置；
5. Vite、Playwright、数据脚本使用 `process.cwd()`、`import.meta.url` 与真实路径解析，不再写死盘符；
6. 在 README 增加唯一启动方式。

原计划优先尝试从仓库根目录直接导入微信开发者工具。实际验证发现，开发者工具会扫描根目录约 3.7 万个 Web 依赖文件，并持续复用首次导入时生成的无 AppID 项目缓存，导致模拟器 60 秒超时和自动化端口缺少 `SDKVersion`。项目级缓存清理和主进程重启均无法稳定消除该平台行为，因此按 7.6 的回滚策略，将 `miniapp/` 固化为唯一受支持的微信入口。

### 7.4 预计修改范围

- `miniapp/project.config.json`
- `vite.config.js`
- `package.json`
- `README.md`
- 新增路径一致性测试或检查脚本
- 小程序组件配置中的绝对路径改为相对路径

### 7.5 验收标准

- `D:\art` 和 `E:\CodexProjects\art` 执行 `npm run build` 均通过；
- 从 `<仓库根目录>\miniapp` 打开开发者工具可以正常启动模拟器；
- 从命令行启动自动化端口后可以连接首页；
- 路径配置不包含开发者个人 Node 安装目录；
- README 只提供一套正式启动方式；
- 不影响现有 CloudBase 环境和 AppID。

### 7.6 回滚

如需回滚，恢复 Vite 默认根路径和原有小程序配置；但不得同时保留根目录与 `miniapp/` 两份微信项目配置，否则会重新引入入口歧义。

### 7.7 执行结果（2026-07-29）

- 状态：已完成；
- `npm run check:entry`：`D:\art` 与真实路径均通过；
- `npm run test:entry`：3/3 通过，覆盖正确入口、重复配置和错误根路径；
- `npm run check`：通过；
- `npm run build`：
  - `D:\art` 通过；
  - `E:\CodexProjects\art` 通过；
- 微信开发者工具：
  - `cli.bat auto --project D:\art\miniapp --auto-port 9443 --trust-project` 启动成功；
  - `miniprogram-automator` 连接成功；
  - `reLaunch("/pages/home/home")` 返回 `pages/home/home`；
- 未修改 CloudBase 数据、云环境或 AppID；
- 未改变页面视觉；组件引用只做了等价的相对路径修正。

## 9. 任务三：修复生产分类与推荐数据漂移

### 9.1 问题

生产推荐审计当前返回：

- 缺失作品—标签关系：83；
- 多余关系：8；
- 频道数量不一致：6；
- `ok: false`。

这会导致：

- 作品出现在错误题材中；
- 正确作品无法通过题材找到；
- 首页中声明为严格分类的频道与分类页结果不一致；
- 频道声明数量与实际查询数量不同。

### 9.2 目标

建立两套职责不同、但版本和数据来源可追溯的内容体系：

1. **严格分类体系**用于分类页和标签页：
   - `artworks.classification_ids`
   - `artwork_tag_links`
   - `vocab_terms`
   - 小程序本地分类目录
2. **多元推荐体系**用于首页：
   - `recommendation_channels`
   - 推荐信号、画家维度、主题策展和视觉特征
   - 频道作品统计

两套体系不要求拥有相同的频道或相同的作品集合。首页可以比分类页更广泛、多元，但不得把推荐信号伪装成严格作品分类。只有声明为 `classification` 来源的首页频道，才必须与对应分类页使用同一份受控关系。

### 9.3 实施步骤

1. 保存当前生产快照和审计报告；
2. 对 91 条关系差异逐条生成修复原因：
   - 受控词表迁移；
   - 人工审核修正；
   - 旧发布残留；
   - 频道统计未重算；
3. 重点人工复核已知问题：
   - 鱼类图谱不能归入植物题材；
   - 《宫娥》不能归入植物题材；
   - 《1808年5月3日》不能归入植物题材；
4. 生成确定性的修复包：
   - additions；
   - removals；
   - artwork patches；
   - channel count patches；
   - rollback；
5. 为每个首页频道标记明确的来源类型：
   - `classification`：严格分类；
   - `artist`：画家维度；
   - `recommendation_signal`：主题、情绪、视觉或内容信号；
   - `editorial`：人工策展组合；
6. dry-run 分别验证严格分类关系和推荐频道候选池；
7. pilot 写入少量已知样本；
8. 在小程序分类页、首页频道和查看更多页分别回读；
9. 正式写入；
10. 分来源类型重算频道统计；
11. 再次执行生产审计和查询冒烟。

### 9.4 安全边界

- 不根据作品标题中的单个关键词直接写入生产标签；
- 不把画家标签与作品分类混用；
- 推荐信号可以用于首页候选池，但不能反写为严格分类标签；
- 不修改未进入修复包的作品；
- 不覆盖人工审核字段；
- 每条写入必须有 rollback 对应项。

### 9.5 验收标准

- `recommendation:audit` 返回 `ok: true`；
- missing/unexpected tag links 均为 0；
- channel count mismatches 为 0；
- 已知错误作品不再出现在植物题材；
- 植物题材抽样结果均有可解释的视觉或结构化证据；
- 分类页与标签页使用同一套严格分类关系；
- 首页频道可以比分类页更多元，支持画家、主题、情绪、视觉特征和人工策展等来源；
- 声明为 `classification` 的首页频道与对应分类页口径一致；
- 非分类型首页频道具有明确的来源类型、候选规则和可解释证据，不会反向污染严格分类；
- 随机刷新仍然只在频道范围内执行；
- 正式写入可以重复执行且保持幂等。

1. 明确 Web/PWA 是否仍是正式产品运行面：
   - 是：迁移为独立 workspace/package；
   - 否：转为明确的 legacy/工具目录，不再进入小程序门禁；
2. 拆分 `artworks.js`：
   - repository/query；
   - normalization；
   - search；
   - recommendation；
   - classification；
3. 拆分 `account.js`：
   - identity/profile；
   - achievements；
   - sync；
   - cache；
4. 拆分 `home.js`：
   - feed state；
   - search state；
   - section pagination；
   - page adapter；
5. 将低频页面迁移到分包：
   - account-data；
   - profile-edit；
   - achievements；
   - help/about/legal；
6. 测量：
   - 主包大小；
   - 首屏时间；
   - 首页云请求数；
   - 图片失败率；
   - 页面 setData 次数和数据量；
7. 每次只拆分一个领域，保持行为测试不变。

### 16.4 验收标准

- 主包体积明显下降且不超过平台限制；
- 首页首屏和交互时间不劣化；
- 大型模块具有清晰职责边界；
- Web 与小程序依赖不再互相污染；
- 所有既有测试继续通过；
- 不在同一任务中同时重构数据模型和视觉。
